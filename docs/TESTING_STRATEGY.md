# استراتيجية الاختبار — كيف نختبر التطبيق فعليًا

> الوثيقة تجيب سؤالًا واحدًا: ما الذي نعتبره «مُختبَرًا»، وكيف نثبته قبل أي دمج.

## 1. لماذا نجحت الاختبارات ومع ذلك ظهرت أخطاء؟

131 اختبارًا كانت تنجح، ومع ذلك اكتشف Cubic أخطاء P1. السبب ليس ضعف عدد الاختبارات، بل ثلاثة أنماط:

| النمط | المثال الحقيقي | الإصلاح |
|---|---|---|
| اختبار يختبر التنفيذ لا العقد | اختبار ترحيل v1 كان يفتح DB **فارغة**، فينجح رغم أن الأحداث القديمة لا تُفهرس | ابنِ بيانات في الحالة القديمة قبل الترقية (نُفّذ في `fts_search_test.dart`) |
| حالة واحدة فقط | `TimezoneStatus.utc` مكتوبة دائمًا حتى بلا تاريخ | اختبار لكل حالة enum، بما فيها `invalid` |
| وهم التغطية | 909 أسطر واجهة في `app.dart` مع widget tests قليلة | golden + integration + اختبارات حالات |

القاعدة: **الاختبار يجب أن يفشل قبل الإصلاح.** إن كتبت اختبارًا ينجح على الكود القديم، فهو لا يحمي شيئًا.

## 2. طبقات الاختبار

### أ. وحدات (سريعة، كل commit)

- محوّلات JSON لكل شكل مدعوم، وحقول ناقصة/زائدة.
- تطبيع التواريخ والمناطق الزمنية، بما فيها `invalid`.
- تطبيع النص العربي والاستعلامات العدائية.
- حدود الحجم والمسارات وأعلام ZIP.
- كل رمز في `import_error_catalog` له رسالتان ar/en وإجراء.

### ب. قاعدة بيانات وتكامل (كل commit)

- إنشاء المخطط من الصفر.
- **مصفوفة ترحيل**: v1→v2، v2→v3، v3→v4، v1→v4، مع بيانات في كل خطوة.
- معاملة تفشل في المنتصف → rollback كامل ولا صفوف يتيمة.
- حذف استيراد → cascade صحيح على `events/source_files/attachments/event_search`.
- بحث FTS بعد insert/update/delete.
- إلغاء استيراد → لا staging ولا صفوف.

### ج. واجهة (widget + golden)

- RTL/LTR، تبديل اللغة.
- تنقل بلوحة المفاتيح وترتيب focus.
- حالات: تحميل، فارغ، خطأ، نتائج صفر مع مرشحات.
- بطاقة إحصاء تفتح نفس سجلاتها (نفس predicate).
- **Golden tests** للشاشات الحرجة: Overview, Search, Timeline, Import report, Settings. المقارنة صورية، فتكشف الانزياح البصري غير المقصود.

### د. تكامل حقيقي (integration_test)

هذه الطبقة الغائبة تمامًا اليوم، وهي التي تجيب «هل التطبيق يعمل؟»:

1. تشغيل التطبيق على نافذة Desktop حقيقية.
2. اختيار أرشيف fixture صناعي.
3. متابعة شريط التقدم حتى الاكتمال.
4. البحث عن كلمة معروفة وفتح النتيجة.
5. التحقق من ظهور المصدر.
6. حذف مساحة العمل والعودة لشاشة البداية.

تُشغّل على Windows (CI) وLinux (محليًا)، وليست بديلًا عن اختبار الجهاز الفعلي.

### هـ. أمان وخصوصية

- **صفر شبكة في المستورد**: `HttpOverrides.global` يرمي عند أي طلب، ثم استيراد كامل.
- **صفر شبكة قبل الموافقة** في مسار AI.
- أرشيفات عدائية: EOCD مزيّف، مقطوع، أسماء مكررة بعد Unicode normalization، symlink/hardlink، ZIP داخل ZIP، عمق JSON كبير.
- لا مسار مطلق ولا نص رسالة داخل تقارير الأخطاء أو السجلات.

## 3. كيف تشغّل الاختبارات

```bash
export PATH=$FLUTTER_ROOT/bin:$PATH   # أو مسار Flutter عندك
flutter pub get
flutter analyze          # لازم: No issues found!
flutter test             # لازم: All tests passed!
```

سكربت مختصر يوقف عند أول فشل:

```bash
./tool/verify.sh
```

### تشغيل ملف واحد أثناء التطوير

```bash
flutter test test/data/fts_search_test.dart
flutter test test/services/archive_inspector_test.dart --plain-name "EOCD"
```

### تغطية (عند الحاجة)

```bash
flutter test --coverage
# التقرير في coverage/lcov.info
```

لا نضع نسبة تغطية حدًّا إجباريًا الآن. الأولوية: كل إصلاح P1/P2 يأتي باختبار يفشل قبله.

## 4. مصفوفة الفحص اليدوي قبل الإصدار

لا تُختبر آليًا بالكامل، وتُنفّذ على Windows وLinux:

| السيناريو | المتوقع |
|---|---|
| أول تشغيل بلا بيانات | شاشة بداية، لا أرقام وهمية |
| أرشيف صالح صغير | تقدم حقيقي، ثم ملخص مع تحذيرات إن وجدت |
| أرشيف مقطوع | رسالة مفهومة + رمز آمن، لا crash |
| أرشيف فيه symlink | رفض صريح |
| إلغاء في منتصف الاستيراد | لا صفوف ولا ملفات مؤقتة |
| بحث عربي بتشكيل | يجد النص بلا تشكيل |
| بحث برموز FTS (`"` `*` `NEAR`) | لا crash ولا حقن |
| تبديل اللغة | RTL/LTR سليم، الاقتباسات LTR |
| تكبير النص 200% | لا قصّ ولا تداخل |
| حذف مساحة العمل | حوار تأكيد، ثم عودة للبداية |
| إغلاق أثناء استيراد | لا DB تالفة |

## 5. قاعدة بيانات الاختبار

- ممنوع أي تصدير شخصي حقيقي، حتى محليًا في المستودع.
- fixtures صناعية في `test/fixtures/` أو ملفات JSON صغيرة مولّدة داخل الاختبار.
- أي عينة حقيقية تُنزع هويتها وتُراجع قبل الإضافة، وتُذكر في الوثيقة.
- لا `git add -A`: هذا ما نبّه إليه Cubic، والقاعدة الآن في `AGENTS.md`.

## 6. تعريف «منتهٍ» لأي مهمة

1. اختبار جديد يفشل قبل التغيير وينجح بعده (أو اختبار موجود يثبت السلوك).
2. `flutter analyze` نظيف.
3. `flutter test` كامل أخضر.
4. مراجعة Cubic على الـPR بلا P1/P2 مفتوحة.
5. تحديث `docs/STATUS_AND_PLAN_2026-10-26.md` إن تغيّرت الحالة.

## 7. ما لا يمكن اختباره في هذه البيئة

- تشغيل نافذة Windows حقيقية أو توقيع الحزمة.
- قارئ شاشة فعلي (NVDA/VoiceOver).
- سلوك لوحة المفاتيح على نظام تشغيل بعينه.
- مزوّد AI حقيقي بمفتاح.

هذه تُنفّذ على جهاز المطوّر أو CI، وتُسجّل في PR كـ«متحقَّق يدويًا» لا كـ«ناجح آليًا».
